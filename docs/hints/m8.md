# M8 hints

## Task<T>

1. When the task's body finishes, who should run next, and on whose stack?
2. The promise stores `std::coroutine_handle<> continuation` and a
   `variant<monostate, T, exception_ptr>`. `final_suspend` returns an awaiter
   whose `await_suspend(handle)` returns `handle.promise().continuation` (or
   `std::noop_coroutine()` if none). That's symmetric transfer: the
   compiler turns the resume into a tail call.
3. The `co_await task` awaiter: `await_ready` returns `false` (or
   `handle.done()`). `await_suspend(awaiting)` sets
   `handle.promise().continuation = awaiting` and returns `handle`, which
   starts or resumes the task. `await_resume` rethrows the exception or moves
   the value out. The Task destructor destroys the handle if non-null. Move
   leaves the source null.

## SyncWait

1. With no event loop, how do you drive a lazy task to completion on the current thread?
2. Resume the task's handle directly. With symmetric transfer, it runs to
   completion (if nothing suspends on real I/O), then transfers to
   `noop_coroutine`, which returns to you. Check `handle.done()`, then
   extract the result. If it's not done, something awaited real I/O: that
   is a usage error.

## WhenAll

1. N child tasks, one parent. What counter, where, decremented by whom?
2. Wrap each child in a helper coroutine that awaits it, stores its result
   in slot *i*, then decrements a shared counter at its final suspend. The
   one that brings the counter to zero resumes the parent.
3. The race: children may all finish synchronously during the parent's
   `await_suspend`. Classic fix: start the counter at N+1, and have the
   parent decrement too, *after* starting all children. Whoever reaches zero
   resumes the parent, or `await_suspend` returns false to not suspend at all.

## Blocking IoContext

1. `pread` inside `SubmitRead` completes immediately. Why is resuming the
   coroutine right there a problem for a loop of 200 000 reads?
2. Record the result and push the op on a ready queue. `RunUntilIdle` pops
   and resumes each op until the queue is empty. The resumed coroutine may
   push more.

## io_uring

1. What does `user_data` let you recover when a completion arrives?
2. `SubmitRead`: `sqe = io_uring_get_sqe()`. If null, `io_uring_submit`
   and retry. Then `io_uring_prep_read(sqe, fd, buf, len, offset)`,
   `io_uring_sqe_set_data(sqe, &op)`, and `++in_flight`.
   `RunUntilIdle`: while `in_flight`, call `io_uring_submit_and_wait(1)`.
   For each CQE: copy `res` and `user_data`, then `io_uring_cqe_seen` (or
   batch-advance), `--in_flight`, and resume. Mark seen *before* resuming:
   the resumed coroutine may submit and wait again, re-entering your loop.
3. RAII: a small class owning `struct io_uring` whose destructor calls
   `io_uring_queue_exit`. Destroying the context with ops in flight: wait
   for them first (the kernel will write into memory you don't own anymore).
