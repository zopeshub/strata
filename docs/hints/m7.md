# M7 hints

## Group commit

1. While one thread is inside fsync, other writers arrive. What should they do?
2. Writer queue: `std::deque<Writer*>` under the DB mutex. Each `Writer` has
   `batch`, `sync`, `done`, `status`, and a condition variable (or use one CV
   plus predicate checks). A writer enqueues itself, then waits until
   `done || it is the front`. If done, it returns its status.
3. The front writer is the leader. It builds a group: itself plus
   followers behind it, up to ~1 MB. It must not include a sync writer
   in a group whose leader is non-sync (or it must upgrade the group to
   sync). It concatenates the batches (`WriteBatch::Append`), assigns
   sequence numbers, **unlocks**, appends one WAL record, Syncs if needed,
   and applies to the memtable. It relocks, then pops and marks every
   member done with the same status. It signals the new front.
   Memtable inserts by the leader run while followers wait; that is safe
   because only one leader exists at a time.

## Write stalls

1. Where in the write path do you check L0 size, and with what lock held?
2. In "make room for write" (leader only, mutex held): if L0 ≥ slowdown
   and we haven't delayed yet, unlock, sleep 1 ms, and relock. If `imm_` is
   still flushing, or L0 ≥ stop, `bg_cv_.wait(...)` until that changes. All
   of it is skipped when auto compactions are disabled.

## Sticky background error

1. Which writes may still succeed after a WAL sync failed?
2. None. Set `bg_error_` on any sync, flush, or compaction failure. Every
   write path checks it first (leader and followers). `WaitForBackgroundWork`
   returns it too. A failed WAL sync also means: the memtable must **not**
   receive that batch (you haven't acknowledged it). What if you already
   applied it? (You shouldn't have: apply after the sync.)

## Shutdown

1. The destructor runs while a background compaction is mid-flight. What must happen before members die?
2. Set `shutting_down_`, notify, and wait for the background thread to
   finish its current job and exit (or `jthread` stop + join). The
   background job checks the flag between steps and abandons outputs.
