# M3 hints

## Arena

1. Most allocations are tiny, and some values are huge. What happens to the
   rest of a 4 KiB block if a 3 KiB value arrives when 2 KiB are left?
2. Keep `alloc_ptr_` and `remaining_` for the current block, and a
   `vector<unique_ptr<char[]>>` of all blocks. Requests > 1 KiB get a
   dedicated block, and the current block keeps being used for small ones.
3. `AllocateAligned`: `mod = reinterpret_cast<uintptr_t>(alloc_ptr_) & (align - 1)`;
   `slop = mod ? align - mod : 0`. If `bytes + slop <= remaining_`, bump.
   Otherwise take a new block: `new char[]` is aligned for any fundamental
   type. `MemoryUsage` is an `atomic<size_t>`, updated with `relaxed` order.
   Why is relaxed enough for a number that is only a flush heuristic?

## Skiplist node layout

1. A node needs a key and `height` next pointers, and the height is only
   known at runtime. How do you allocate that as one arena chunk?
2. Allocate `sizeof(Node) + sizeof(atomic<Node*>) * (height - 1)` and
   placement-new the Node (which declares `std::atomic<Node*> next_[1]`).
   Then placement-new the extra atomics. Indexing `next_[i]` for `i >= 1` is
   technically out of bounds of the declared array. Write down why LevelDB
   gets away with it, and what a conforming alternative is (e.g. store the
   pointers *before* the node, or compute `reinterpret_cast<atomic<Node*>*>(this + 1)`
   with objects placement-newed there).
3. `std::launder`: needed when you reuse storage and access the new object
   through a pointer to the old one. With the pointer returned by placement
   new, you don't. Be able to say exactly this.

## Memory orders

1. The writer initializes a node, then makes it reachable. The reader
   follows pointers. Which pair of operations must form a synchronizes-with edge?
2. `SetNext(i, x)` = `next_[i].store(x, release)`. `Next(i)` =
   `next_[i].load(acquire)`. While building the new node before publication,
   its own next pointers can be set with `relaxed` (`NoBarrier_SetNext`):
   nobody can see the node yet.
3. Insert: find `prev[]` at every level (`FindGreaterOrEqual`). Pick a
   height. If it's > `max_height_`, fill `prev[]` for the new levels with head
   and `max_height_.store(h, relaxed)`. A reader seeing the new height early
   just finds head→nullptr at those levels, which is harmless. Then for
   `i = 0..h-1`: `x->NoBarrier_SetNext(i, prev[i]->NoBarrier_Next(i));
   prev[i]->SetNext(i, x)`. Bottom-up.

## MemTable on the skiplist

1. The skiplist key is a single `const char*`. How does the comparator find
   the internal key inside the entry?
2. Entry = `varint32(klen) internal_key varint32(vlen) value`, one arena
   allocation. The comparator decodes the length prefix of both entries, then
   compares with `InternalKeyComparator`.
3. `Get`: build the lookup entry (the memtable key = length-prefixed internal
   key from `LookupKey`), `iter.Seek(that)`, and check the user key. The
   DB-level change: `Get` copies `shared_ptr<MemTable>` under the mutex,
   *drops the mutex*, then reads.
